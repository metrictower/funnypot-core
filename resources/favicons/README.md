# Persona-coherent favicons (FP-0230)

These `.ico` files are **self-generated collision blobs**, not vendor artwork.

## What they are

Each icon is a plain, self-drawn 16×16 geometric mark (a colored ring on a transparent
background — no logo, no wordmark, no vendor artwork) whose Shodan/FOFA/lonkero favicon hash
(`murmurhash3_x86_32(base64.encodebytes(bytes))`, signed int32 — see
`src/Support/FaviconHash.php`) **equals a known product signature**. A hash-only fingerprinter
indexes the host as that product; it does not render or pixel-compare the icon, which is the
entire payoff (spec §3). The residual tell — the icon does not *look* like the vendor logo — is a
strictly higher bar (a human analyst / render-and-compare scanner) that this threat model and this
codebase do not otherwise defend.

## Provenance (why this is license-clean)

A favicon hash is a function of exact bytes. To match a published product signature there are two
byte sources: (A) the vendor's real favicon — its logo/wordmark, trademark-protected and carved out
of the code license even for GPL/AGPL OSS, clearing neither `resources/ALLOWED-LICENSES.txt`
(MIT/Apache-2.0/BSD-2/BSD-3/CC0) nor `scripts/ci/check-license.sh`; or (B) **self-generated bytes
that collide to the same 32-bit value**. MurmurHash3-32 is a non-cryptographic 32-bit hash, so a
preimage for a chosen target is brute-forceable offline in ~2^32 trials (seconds in C). We author a
generic icon and vary 6 benign trailing bytes (past the ICO image data, which decoders ignore) until
the hash matches. **The bytes are ours; a 32-bit integer is not copyrightable → provenance is clean.**
No vendor binary is committed.

## The forge (dev-bench only, never on the serve path)

`scripts/dev/favicon/forge.c` — `cc -O2 -o forge forge.c`, then:

| Asset            | Product      | Signature (signed int32) | Command                          |
|------------------|--------------|--------------------------|----------------------------------|
| `grafana.ico`    | Grafana      | `999357577`              | `./forge 999357577 3b7dd8 0`     |
| `phpmyadmin.ico` | phpMyAdmin   | `-1588080585`            | `./forge -1588080585 c07830 0`   |
| `jenkins.ico`    | Jenkins      | `81586312`               | `./forge 81586312 d33833 0`      |
| `tomcat.ico`     | Tomcat       | `116323821`              | `./forge 116323821 6f9a3b 0`     |
| `neutral.ico`    | (none)       | `891788695` — not a known signature | `./forge neutral`     |

Each hash-match is re-verified by the committed PHP `FaviconHash` (independent of the C forge) in
`tests/FaviconRoutingTest` (per-asset + end-to-end serve). The favicon-hash algorithm itself is
pinned to the scanner reference by an independent C oracle KAT in `tests/Support/FaviconHashTest`.

## Coverage

Forged: **Grafana, phpMyAdmin, Jenkins, Tomcat** (each has a real decoy page whose
`<link rel="icon">` points at its hash-matching favicon — within-page coherence).

Extensible / deferred (no icon yet; a no-signature persona serves the neutral favicon, never a
mismatched one): cPanel `988422585`, Kibana `-962726853`, Joomla `1354567968`, WordPress
`-335242539`, Nginx `1485257654`, Apache `-297069493`, Drupal `-1395229095`, phpMyAdmin variants.
Add one by forging the asset (above), dropping a `templates/route/NNN-<product>-favicon.yaml`
binary route, pointing the product page's `<link rel="icon">` at it, and rebuilding the index.

The bare-root `/favicon.ico` serves `neutral.ico` (contradicts nothing); matching it to the
`/`-lottery persona needs the global per-attacker family selector deferred in PERSONA-CAP §6.
